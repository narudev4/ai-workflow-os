# Requirement Definition

## 方針

Walkers の要件定義は、詳細設計まで詰め切るものではありません。

先方と合意できる粒度で、要求、画面、機能、工程、質問、テストケースを整理することが目的です。

## 標準工程

```text
要求整理
  -> 画面一覧
  -> 機能一覧
  -> 工程表
  -> 質問表
  -> テストケース
  -> 先方確認
  -> 合意
```

## 各工程の完了条件

### 要求整理

Done:

- モック、議事録、先方発言から要求を抽出している
- 要求の目的、利用者、業務背景を分けている
- 未確認の前提を questions.csv に送っている

### 画面一覧

Done:

- モック上の画面を全列挙している
- 主要な状態、権限、例外候補を見ている
- 関連機能と未確定事項が紐づいている

### 機能一覧

Done:

- 各画面の主要機能を洗い出している
- 正常系だけでなく、異常系、権限、状態遷移、外部連携を見ている
- 実装詳細ではなく要件定義レベルで止めている

### 工程表

Done:

- 要件定義、実装、確認、修正、納品の流れが見える
- 不明点がある工程にはリスクが記載されている
- クライアント確認が必要なタイミングを示している

### 質問表

Done:

- 画面一覧、機能一覧、工程表から生じた未確定事項を列挙している
- なぜ確認が必要かが書かれている
- 回答が得られたら requirements / screens / features / schedule / testcases のどこへ反映するか分かる

### テストケース

Done:

- 主要な正常系、異常系、権限、状態の確認観点がある
- どの画面・機能に紐づくか分かる
- 先方合意に必要な確認粒度に留めている

## 詳細設計に入らないための境界

次が出始めたら別工程に切り出す。

- DBテーブルの具体設計
- APIエンドポイントの詳細
- コンポーネント構成
- ライブラリ選定の細部
- 実装順序の詳細タスク分解
